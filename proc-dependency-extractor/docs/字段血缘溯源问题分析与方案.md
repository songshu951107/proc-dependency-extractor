# 字段血缘溯源问题分析与方案

> 探讨日期：2026-08-06
> 涉及模块：存储过程血缘分析 → 字段来源（第二个 Tab）→ "最终来源（溯源到非临时表）"列
> 核心问题：字段来源为临时表时，最后一列"最终来源表"仍显示临时表，未溯源到非临时表

---

## 一、问题背景

系统「存储过程列表 → 血缘分析」第二个 Tab 页（`FieldSourceList.vue`）展示目标表每个字段的来源信息，共四列：

| 列 | 含义 |
|---|---|
| 目标字段 | 目标表的字段名 |
| 来源表达式 | SELECT 中的源表达式原文 |
| 来源表 | 直接来源表（可能是临时表 VT_） |
| **最终来源（溯源到非临时表）** | 沿临时表链递归，溯源到第一个非临时表的字段 |

**期望**：当"来源表"是临时表（`VT_` 开头）时，"最终来源"列应显示溯源到底的非临时表字段。

**实际 Bug**：部分字段的"最终来源表"仍是临时表（如 `VT_C`），未溯源到 `F_A` 这类源表。

---

## 二、根因分析

### 2.1 溯源链路

- **入库侧**（`FieldMappingExtractor`）：用 DDL 字段字典做正向匹配，`target_field` 来自 DDL 字段名，**稳定可靠**。
  - `LineageExtractor.java:222` 从 `CREATE TEMP` 内联 DDL 提取字段缓存
  - `FieldMappingExtractor.java:78-143` 按 `AS alias → alias.field → 位置` 三级匹配
- **查询溯源侧**（`LineageServiceImpl.traceUltimateSource`）：从 `sourceExpr` 里**猜**一个字段名去匹配下层临时表的 `target_field`，**脆弱**。
  - `LineageServiceImpl.java:265-266` 递归时调 `extractFieldFromExpr(sourceExpr)`
  - `LineageServiceImpl.java:308-327` `extractFieldFromExpr` 实现

**矛盾点**：入库用 DDL 字典正向匹配（稳），溯源用表达式猜字段反向匹配（脆），两侧方法不一致，这是根因。

### 2.2 `extractFieldFromExpr` 的缺陷

`LineageServiceImpl.java:308-327`，提取优先级：
1. `CASE WHEN ... THEN alias.field` → 取 THEN 后的 field
2. 非 CASE → **取最后一个** `alias.field` 的 field 部分
3. 无 `alias.field` → 返回表达式小写

**规则2"取最后一个"是主要错误源**。对多字段表达式，最后一个参数往往不是主字段。

### 2.3 兜底逻辑放大问题

`LineageServiceImpl.java:264-277`：

```java
if (isTempTableName(sourceTable)) {
    UltimateSource deeper = traceUltimateSource(procName, sourceTable,
            extractFieldFromExpr(fm.getSourceExpr()), visited);
    if (deeper != null) {
        // 用更深层结果 ✅
    } else {
        // ⚠️ 递归失败时，把这个临时表当成"最终来源"返回！
        result.setSourceTable(sourceTable);      // 仍是 VT_xxx
        result.setSourceTableType("TEMP");
        result.setSourceField(extractFieldFromExpr(fm.getSourceExpr()));
    }
}
```

递归失败（`deeper == null`）时，兜底把临时表冒充最终来源返回 → 前端"最终来源"列显示临时表。

### 2.4 递归返回 null 的 4 种触发场景

`traceUltimateSource`（`LineageServiceImpl.java:228-251`）返回 null 的情况：

| # | 触发条件 | 典型原因 |
|---|---|---|
| 1 | `tempField == null` | `extractFieldFromExpr` 对 `COUNT(*)` 等提取不出字段名 |
| 2 | `edges.isEmpty()` | 该临时表没有作为 `target_table` 的 lineage 边（CREATE TEMP 字段映射未入库，或 `target_table_short` 命名不一致） |
| 3 | `mappings.isEmpty()` | **字段名匹配不上**：`extractFieldFromExpr` 提取的字段名与临时表实际存的 `target_field` 对不上，`equalsIgnoreCase` 也救不回来 |
| 4 | `visited.contains(key)` | 临时表链出现环路（A→B→A），防环直接返回 null |

**场景3是本项目最常见的**，由 2.2 的"取最后一个"规则导致。

## 三、端到端验证（已复现 Bug）

### 3.1 验证方式

构造多层临时表链 `F_A → VT_C → VT_B → TARGET_TABLE`，关键在 `VT_B → VT_C` 段：
- `VT_C.M_AVG` 来自 `F_A.m_avg`（最终来源应是 `F_A.m_avg`）
- `VT_B.kh_mavg` 的来源表达式是 `DECODE(T7.M_AVG, T8.B, 0)`（T7 指向 VT_C，真实依赖 `VT_C.M_AVG`）
- `TARGET_TABLE.out_field` 来自 `VT_B.kh_mavg`

测试文件：
- `src/test/java/com/hb/extractor/service/UltimateSourceTraceTest.java`（标准 `@SpringBootTest`，IDEA 可直接跑）
- `src/test/java/com/hb/extractor/UltimateSourceVerifyApp.java`（独立 Spring main，命令行可跑）

### 3.2 验证结果

**独立 main 验证 `extractFieldFromExpr` 行为**（零依赖）：

```
expr: DECODE(T7.M_AVG, T8.B, 0)   -> extracted: b        ← 取了 T8.B，不是主字段 M_AVG！
expr: NVL(a.x, b.y)               -> extracted: y        ← 取最后一个
expr: a.x + b.y + c.z             -> extracted: z        ← 取最后一个
expr: T01.m_avg                   -> extracted: m_avg    ← 单字段才正确
expr: SUM(CASE WHEN ... THEN LR_DISTR.dist_amt_thmonth END) -> dist_amt_thmonth  ← CASE THEN 正确
```

**端到端验证结果**（启动 Spring 上下文 + 真实 MySQL）：

```
targetField      = out_field
direct source    = VT_B / T9.kh_mavg
ultimateSource.sourceTable     = VT_C        ← 最终来源仍是临时表！
ultimateSource.sourceTableType = TEMP
ultimateSource.sourceField     = b           ← 提取错了（应为 m_avg）
ultimateSource.path            = [VT_B.kh_mavg, VT_C.b]   ← 卡在 VT_C，没到 F_A
[复现BUG] 最终来源仍是临时表 VT_C（应为 F_A）
```

### 3.3 完整因果链（已坐实）

| 步骤 | 发生了什么 | 证据 |
|---|---|---|
| 1 | 表达式 `DECODE(T7.M_AVG, T8.B, 0)` 真实依赖 VT_C.M_AVG | SQL 语义 |
| 2 | `extractFieldFromExpr` 规则2"取最后一个 alias.field" → 取到 `b`（T8.B） | 独立 main 验证 + 代码 `LineageServiceImpl.java:316-323` |
| 3 | 递归进 VT_C 时用 `b` 匹配 `target_field=M_AVG` → 失败 | DB 里 VT_C 的 target_field 是 `M_AVG`，`b`≠`M_AVG` |
| 4 | 兜底把 VT_C 当最终来源返回，sourceField=`b` | 端到端输出 `sourceTable=VT_C, sourceField=b` |

期望结果应是 `F_A.m_avg`（沿 `VT_C.M_AVG ← F_A.m_avg` 追溯到底）。

## 四、方案对比

### 4.1 场景3（字段名匹配不上）修复方案

核心思路：把溯源侧从"从表达式猜字段"改成"用字段字典去表达式里找"。

| 方案 | 字典来源 | 做法 | 改动量 | 依赖 |
|---|---|---|---|---|
| **A（推荐）** | 下层临时表**已有的 mappings 的 target_field 集合** | 递归进下层前不调 `extractFieldFromExpr`；取下层 `allMappings` 的 `target_field` 列表作候选，在这些候选字段里找哪个出现在 `sourceExpr` 中 | 小，只改 `traceUltimateSource` | 无需 DDL，无需改入库 |
| **B** | 下层临时表的 **DDL 字段列表** | trace 时取该临时表的 CREATE TEMP DDL / DDL 文件字段，在 `sourceExpr` 里找 | 中 | 需把 parse 期的 `tempTableDdlFields` 缓存持久化（目前是局部变量，trace 时已丢失），或解析时落库 |
| **C** | 治本：存储侧保证 `target_field` 一律来自 DDL | 修复入库，无 DDL 时也用稳定规则；溯源侧直接用 `sourceExpr` 引用字段匹配 | 大 | 需重新解析入库所有存储过程，历史数据要重跑 |
| **D** | A + C | 先上 A 作安全网，再治本 C | 最大 | 最稳 |

### 4.2 为什么推荐方案 A

1. **字典和 `target_field` 同源**——`allMappings` 的 `target_field` 就是入库时定的最终字段名，用它做候选去表达式里找，天然和入库一致，不会出现"猜的名字 vs 存的名字"错位。
2. **零额外依赖**——`allMappings` 在 `traceUltimateSource` 里已查出（`LineageServiceImpl.java:244-250`），只是现在只拿它做 `equalsIgnoreCase` 过滤。改成"先精确匹配，匹配不到再反向在 `sourceExpr` 里找候选字段"即可，不碰 DDL 持久化、不碰入库。
3. **比 B 覆盖更广**——本项目存在"无 DDL 靠 AS 别名入库"的路径（`FieldMappingExtractor.java:144` else 分支）。这种表 B 拿不到 DDL 字典，A 却能拿到（mappings 的 target_field 就是别名/位置名）。
4. **A 和 C 不冲突**——A 是查询侧鲁棒化，C 是存储侧规范化，可分阶段做，A 先上是 C 的安全网。

> **关于"是否依赖 DDL"的讨论结论**：A 不是"不用 DDL"，是"用了 DDL 的结果，没用 DDL 的来源"。mappings 的 `target_field` 本身就来自 DDL（DDL 命中时）。A 和 B 的字典本质同源，区别仅在覆盖面：A = "DDL 字段 ∩ 已有 mappings"，B = "DDL 全集"。正因有"无 DDL 靠别名"的入库路径，B 依赖 DDL 反而有盲区，A 覆盖更全。

### 4.3 兜底改造（与方案 A 配套）

`LineageServiceImpl.java:272-277` 的 else 分支改为 `return null`。溯源不到非临时表就整体返回 null，前端该格显示 `-`，不再用临时表冒充最终来源。

| 兜底方案 | 做法 |
|---|---|
| **A（最小改动）** | else 改 `return null`，前端显示 `-`。丢失"卡在哪个临时表"线索 |
| **A+（推荐增强）** | A 基础上返回 `stuckAt`/`path` 线索，前端 `-` 旁加 tooltip 提示溯源中断于哪个临时表 |

## 五、方案 A 反向匹配规则（已实测验证）

### 5.1 规则定义

给定 `sourceExpr` 和候选字段集（下层 mappings 的 `target_field`），在 expr 里反向找引用，优先级：

1. `THEN alias.field` 命中候选 → 取它（CASE WHEN 取值分支）
2. `alias.field` 命中候选 → 取**第一个出现**的（纠正当前"取最后一个"的错误）
3. 裸字段命中候选 → 取第一个
4. 都没命中 → null（配合兜底返回 null，前端显示 `-`）

> **注意**：规则2"取第一个出现"必须按 `alias.field` 在 expr 中的**出现位置**排序，不能按候选集遍历顺序。验证程序初期版本曾因候选遍历顺序写反，导致 `DECODE(T7.M_AVG, T8.B)` 候选=[M_AVG,B] 误取 B。实现时需按 expr 匹配位置排序。

### 5.2 实测结果（对照当前"取最后一个"实现）

| 表达式 | 候选字段 | 当前实现 | 方案A | 评价 |
|---|---|---|---|---|
| `DECODE(T7.M_AVG, T8.B, 0)` | [M_AVG] | b ❌ | **M_AVG** ✅ | 修正主bug |
| `DECODE(T7.M_AVG, T8.B, 0)` | [M_AVG, B] | b | M_AVG ✅ | 取第一个出现（规则2修正后） |
| `SUM(CASE WHEN A.appl_dt=1 THEN LR_DISTR.dist_amt_thmonth END)` | [APPL_DT, DIST_AMT_THMONTH] | dist_amt_thmonth ✅ | **DIST_AMT_THMONTH** ✅ | 一致 |
| `NVL(a.x, b.y)` | [X, Y] | y ❌ | X ✅ | 取第一个（主值） |
| `NVL(a.x, b.y)` | [Y] | y ✅ | Y ✅ | 一致 |
| `T01.m_avg` | [M_AVG] | m_avg ✅ | M_AVG ✅ | 一致 |
| `a.x + b.y + c.z` | [X,Y,Z] | z ❌ | X ⚠️ | 见第六章多字段运算 |
| `a.x + b.y + c.z` | [Z] | z ✅ | Z ✅ | 一致 |
| `T01.m_avg` | [NOT_EXIST] | m_avg ❌ | **null** ✅ | 候选不在expr→null |
| `COUNT(*)` | [CNT] | t ❌ | **null** ✅ | 同上 |
| `DECODE(CASE WHEN t.f=1 THEN s.g END, 0)` | [F,G] | g ✅ | G ✅ | THEN优先命中 |
| `COALESCE(a.x, b.y, c.z)` | [X,Y,Z] | z ❌ | X ⚠️ | 见第六章多字段运算 |

### 5.3 方案 A 正确解决的（当前实现错的）

- DECODE 单候选、COUNT(*)、候选不在 expr 中 → 从"取错/取到无意义值"变成 null 或正确值
- "取第一个 alias.field" 比"取最后一个"更符合 SQL 语义：DECODE/NVL/COALESCE 的主值通常在第一个参数

## 六、待决问题：多字段运算表达式（如 `B.acct_bal * C.rate`）

### 6.1 本质

`out_field = B.acct_bal * C.rate` 是**乘法表达式**——两个字段都是真实的、平等的依赖，没有"主字段"之说。与 `DECODE`/`NVL` 不同：

| 表达式 | 真实依赖 | "主字段"概念 | 单字段溯源是否合理 |
|---|---|---|---|
| `DECODE(T7.M_AVG, T8.B, 0)` | M_AVG 主值，B 匹配条件 | ✅ 有 | ✅ 合理 |
| `NVL(a.x, b.y)` | x 优先，y 兜底 | ✅ 有（x） | ✅ 合理 |
| `B.acct_bal * C.rate` | 两个字段都参与计算 | ❌ 没有 | ⚠️ 取任一个都不全 |
| `a.x + b.y` | 同上 | ❌ 没有 | ⚠️ 同上 |

对乘法/加法这类**多字段运算**，溯源到"单个最终来源字段"本身就是信息损失——改 `acct_bal` 或改 `rate` 都会影响 `out_field`。

### 6.2 当前实现的错误

`extractFieldFromExpr` 取最后一个 `alias.field` → 对 `B.acct_bal * C.rate` 取 `rate`。只溯源 `rate` 一条链，`acct_bal` 那条链丢失。前端"最终来源"列只显示一个，且**漏掉了另一个真实依赖**。

### 6.3 候选方向（待用户拍板）

| 方向 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **方向1：取第一个，单值** | 多字段运算取第一个出现的候选字段（如 acct_bal），结构不变 | 简单，与方案A规则一致 | 漏掉其他依赖 |
| **方向2：全部依赖，改多值列（推荐）** | "最终来源"改为多值，acct_bal 和 rate 都溯源展示。后端 `ultimateSource` 改为 `List<UltimateSource>`，前端改列展示 | 语义最完整，真正字段级血缘 | 改动较大 |
| **方向3：运算式不溯源，标记多源** | 含 `+ - * /` 的表达式返回 null + `multiSource: true`，前端显示"多源派生" | 不误导 | 牺牲溯源深度 |
| **方向1+标注** | 取第一个候选字段，但命中候选 >1 时加 `multiSource: true` 标记，前端提示还有其他依赖 | 不大改结构且不假装单一来源 | 仍只溯源一条链 |

### 6.4 选型建议

- 若"最终来源"列给**数据探查/口径确认**用 → 方向2 最对，但成本高
- 若给**影响分析快速定位**用 → 已有字段级影响分析（`MAPS_TO` 图）承担主要责任，方向1 够用、成本低
- 若**绝不希望误导** → 方向3 最稳

**待用户确认**：`B.acct_bal * C.rate` 这类多字段运算表达式，"最终来源"列希望怎么处理？选型未定前不实现第六章。

## 七、图数据库能否解决此问题

### 7.1 结论：不能直接解决，症结相同

症结是"从表达式猜字段"，而**图数据库建边时用的是同一个猜法**。

| 环节 | 用的字段提取逻辑 | 结果 |
|---|---|---|
| 字段映射入库 (`table_field_mapping`) | DDL 字典匹配（`FieldMappingExtractor`，稳） | target_field 正确 |
| Neo4j 建 `MAPS_TO` 边的 source Column | `extractFieldName(sourceExpr)`（猜，`Neo4jSyncServiceImpl.java:461`） | `(\w+)\.(\w+)` 取第一个匹配 |
| 溯源查询 (`traceUltimateSource`) | `extractFieldFromExpr(sourceExpr)`（猜，取最后一个匹配） | 取最后一个 |

**关键发现**：Neo4j 那边 `extractFieldName`（`Neo4jSyncServiceImpl.java:461-466`，`FIELD_PATTERN = (\\w+)\\.(\\w+)` 取 `m.find()` 第一个）与溯源用的 `extractFieldFromExpr`（取最后一个）连"猜的规则"都不一致。对 `DECODE(T7.M_AVG, T8.B, 0)`：
- Neo4j 建边时 source Column = `M_AVG`（第一个）
- 溯源时猜的是 `b`（最后一个）

所以哪怕改用 Neo4j 查 `MAPS_TO`，**边的 source 端 Column 节点本身也是猜出来的**——图数据库只是把"猜错的结果"换了个地方存，没有从根本上解决"如何从 `DECODE(...)` 里确定主字段"。

### 7.2 图数据库能带来的间接好处

如果配合方案 A 的反向匹配思路，用图做查询会更顺：
1. **天然的路径查询**——`MATCH (t:Column)<-[:MAPS_TO*1..10]-(src:Column) WHERE src 所属表非临时 RETURN src` 一条 Cypher 替代 Java 递归 + visited 防环。
2. **多入度合并**——一个字段被多个表达式引用时，图天然能聚合所有上游。

但前提是：**边的 source Column 必须建对**。即 `Neo4jSyncServiceImpl.java:159` 的 `extractFieldName` 必须先修对，否则图里存的边就是错的，查询再聪明也是错上加错。

### 7.3 路线对比

| 路线 | 要改的核心 | 额外工作 |
|---|---|---|
| **MySQL（方案A）** | 改 `traceUltimateSource` 的反向匹配 | 无，查询侧单点改动 |
| **Neo4j** | 改 `extractFieldName` 的反向匹配（建边侧） + 重跑全量同步 + 用 Cypher 重写溯源查询 | 重跑入库 + 重写查询，工作量大几倍 |
| **Neo4j + 沿用 MySQL 查询** | 改 `extractFieldName` + 重跑同步，但溯源还查 MySQL | 白做，MySQL 侧问题依旧 |

### 7.4 判断

- **只想快速止血** → 方案 A（改 MySQL 查询侧）最小、最快、零数据迁移。
- **想顺带把 Neo4j 字段级血缘边也建对（治本，以后用图查询）** → 方案 A 的反向匹配逻辑同时套到 `extractFieldName`，再重跑同步。这是 A+C 的图版。
- **纯换 Neo4j 查询、不改提取逻辑** → 解决不了，等于把同一个 bug 搬家。

方案 A 的反向匹配思路**完全可以用在 Neo4j 建边侧**——把 `extractFieldName` 也改成"用候选字段集在 sourceExpr 里反向匹配"，图里的边就建对了。这是治本，但要重跑同步。
