解析（extractAndSave→saveMetadata）：parse() 成功后才 saveMetadata，按 proc_name 对 6 张血缘表先 DELETE 再 INSERT（L428-L440），并重建 proc_info（id 会变）。

两者都是“逐 proc 先删后建”，无整库清空（除非显式 clear-neo4j / deleteProc）。

二、潜在问题
一致性 / 漂移（最该关注）
两端漂移无联动：MySQL 与 Neo4j 是两条独立操作链，系统无“reparse 后强制 resync”的联动。只 reparse 不 resync → Neo4j 仍旧图；只 resync 不 reparse → Neo4j 反映旧血缘。任何一步错配都产出误导结果（符合记忆里的部署教训）。
resync/all 同步长任务易超时中断：中断后 Neo4j 处于“部分 proc 新、部分旧”的混合态，直到本轮跑完。后续必须整段后台跑完，不能当快请求。
事务 / 原子性
extractAndSaveBatch/reExtractAll 外层 @Transactional 包住整批循环，内部逐文件 try/catch——单个文件失败只丢自己、不回滚他人（合理）；但一整批在一个事务里对 299 个 proc 持续持锁，若走 batch 接口会很长。（宽松：reparse_all.ps1 是逐文件调 HTTP，规避了长事务。）
解析失败会吞掉不抛，only 记到 failures 列表——若失败被 skip，该 proc MySQL 不更新，但调用方看到的是“成功 N、失败 M”，没有强制失败即中止的机制。
数据残留 / 孤儿
改名不留痕：saveMetadata 按 procName 删旧，若存储过程改名或文件改名，旧 procName 的 MySQL 血缘与 Neo4j 节点永不清除，形成孤儿数据，污染统计和影响分析（deleteProc 也只能按显式 procName 删）。
同步只清理“该 proc 的 Transform/临时表列”+ 孤儿，物理表共享节点不动——这是对的；但 DWA 自产表没进 columns0818.xlsx 时无 DDL 元数据，裸列归属仍是盲区（记忆里 P-系迭代已部分覆盖，但按需补表仍是手工活）。
图模型 / 多块写入
同一物理列（如 int_income）现拆出多个独立 Transform（3 个 DIRECT + LITERAL + SUM）。正确反映多 UNION 分支，但上游会显示多个并列父节点，且 logicType 推断一变（表达式改写），剪枝逻辑就可能再断链——属既有模型复杂度，需回归测试守护。
transformId 依赖 MySQL 自增 fieldMappingId，而 reparse 会重生成 id。只要“先 reparse 后 resync”顺序对，旧 Transform 已删、按新 id 重建，安全；但若老 jar 与新 jar 实例并存，id 策略不同会造成节点 key 冲突/残留（部署一致性）。
性能
同步逐 proc DETACH DELETE + 重建，单线程串行、无批量 Cypher，299 个 proc 耗时较长，与问题 2 叠加加剧超时风险。
三、建议（按性价比排序）
把“reparse 后须 resync + 重启新 jar”固化成一次校验/提示，或提供一键“reparse→resync 联动”入口。
为 resync/all 改后台任务 + 进度查询（前端暂停 2）而不是长 HTTP。
增加孤儿清扫任务（按 procName 差集清理 MySQL 并同步清理 Neo4j 孤立 Transform/Column）。
保留 130 个单测，把“多块写入列”场景纳入回归（问题 7）。
