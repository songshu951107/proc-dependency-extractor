# 字段级血缘中 ON/WHERE 条件建模问题分析

> 汇总自对 `proc-dependency-extractor` 项目（银行数仓数据血缘系统）的源码核查与讨论。
> 核心问题：**JOIN/WHERE 这类"行级谓词"被当成"列值来源"塞进了字段级值血缘图，并复制进每一个目标列的输入，导致字段级影响分析出现假阳性。**

---

## 一、背景：ON/WHERE 条件在图里到底是"节点"还是"属性"

结论先给：**ON 条件和 WHERE 条件在图里从来不是独立节点**，但要分两个层级看，因为项目在「表级血缘」和「字段级血缘」用了两套不同的建模策略。

### 1. 表级血缘：条件 = `READS` 边上的属性（JSON）

在「表读表」血缘里，JOIN 的 `ON` 和 `WHERE` 既不是节点也不是独立关系边，而是作为 `READS`（源表读取目标表）这条边上的两个 JSON 属性挂着。

代码证据：`Neo4jSyncServiceImpl.createReadsRelationship`（约 383–411 行）

```java
List<TableLineageFilter> joins  = filters.stream().filter(f -> "JOIN".equals(f.getFilterType())).collect(...);
List<TableLineageFilter> wheres = filters.stream().filter(f -> "WHERE".equals(f.getFilterType())).collect(...);
String joinJson  = serializeConditions(joins);
String whereJson = serializeConditions(wheres);

MERGE (src)-[r:READS {proc_name: $procName}]->(tgt)
SET r.operation = $operation,
    r.via_temp  = $viaTemp,
    r.join_conditions  = $joinConditions,   // JSON 文本属性
    r.where_conditions = $whereConditions;  // JSON 文本属性
```

`table_lineage_filter` 表存的每条条件：`filterType`（JOIN/WHERE）、`filterClause`（原文）、`fieldsInvolved`（涉及字段 JSON 数组）。

**设计意图**：表级主体就是"表依赖关系"，条件只是辅助说明，挂边上最省事，查询影响面时不用为条件多跳。

### 2. 字段级血缘：条件里的字段 = 节点，条件 = `role` 属性

到了字段级（列怎么加工成列），走另一条路径：`JsqlSqlAnalyzer.extractConditionFields`（约 236–256 行）把 `ON`/`WHERE` 涉及的字段单独抽出来，打上角色标记：

- ON 条件字段 → `role = "join_condition"`
- WHERE 条件字段 → `role = "where_condition"`

这些字段建成 **`Column` 节点**，通过 `INPUT_TO` 连到 `Transform`（转换）节点，"它来自 JOIN 还是 WHERE"作为 `INPUT_TO` 关系的 **`role` 属性**。

**设计意图**：字段级要回答"某列被哪些列 + 什么条件算出来"，必须把条件里的字段暴露成可遍历节点，用 `role` 区分来源性质。

---

## 二、字段级建模的实际实现方式（问题根源）

`FieldMappingExtractor.extract()`（约 L168–216）把 ON/WHERE 条件字段复制进**每一条**目标列的输入：

```java
List<ColumnRef> conditionFields = analyzer.extractConditionFields(select);
if (!conditionFields.isEmpty()) {
    for (FieldMapping fm : result) {              // 遍历【每一个】目标列
        ...
        for (ColumnRef ref : conditionFields) {
            fm.getInputs().add(ti);               // 把条件字段加进【每一个】目标列的输入
        }
    }
}
```

影响分析遍历时（`ImpactAnalysisServiceImpl.analyzeFieldLevel`，L749–830）无论 DIRECT 还是非 DIRECT 的 Transform，都把每个 input（含 `join_condition`/`where_condition`）建为 `DERIVED_FROM`/`INPUT_TO` 边。`isCondition` 标记**只决定是否补全节点，并没有用来排除边**。

**关键缺陷**：JOIN/WHERE 是**整句级**的（作用于整行），却复制给了所有目标列；且谓词血缘与值血缘混在同一张图里。

---

## 三、具体问题清单

| # | 问题 | 具体表现 |
|---|------|----------|
| 1 | **影响分析假阳性** | 从 `b.balance`（WHERE 条件字段）做下游影响分析，会报告它"影响" `cust_id`/`agreement_no`/`balance` 所有目标列——但 `balance > 0` 只是过滤行，不参与任何列的值计算 |
| 2 | **上游溯源噪音** | 看目标列 `cust_id` 的"值来源"时，会把 `b.cust_id`、`b.balance` 等条件字段混在真正计算它的源字段里，用户分不清"值从哪来"和"行怎么被关联/过滤" |
| 3 | **图边暴涨** | 宽表场景：N 个目标列 × M 个条件字段 = N×M 条多余 `INPUT_TO` 边（如 50 列 × 10 条件 = 500 条），拖慢遍历与渲染 |
| 4 | **虚假共祖** | 所有目标列共享同一批条件字段输入，做"两列共同上游"分析时误判它们强相关 |
| 5 | **语义混淆 + 信息丢失** | 只存了"条件里的字段"，没存条件表达式本体（如 `>`、`0`）；字段级图看不到"为什么用 balance、用什么比较"。谓词血缘与值血缘完全混在一起 |

### 示例（银行数仓典型 INSERT…SELECT）

```sql
INSERT INTO cdm.agreement_summary
SELECT a.cust_id, a.agreement_no, b.balance
FROM fdm.f_cust a
LEFT JOIN fdm.f_account b ON a.cust_id = b.cust_id
WHERE a.stat_dt = DATE '{I_LAST_DT}' AND b.balance > 0;
```

按当前实现，`b.balance`（WHERE 字段）会错误地与 `cust_id`、`agreement_no` 两个目标列建立值血缘边——但实际上它只过滤行，不贡献任何列的值。

---

## 四、为什么会产生这个问题

- **设计者意图可能有用**：保留条件字段便于回答"哪些列参与了关联/过滤"。
- **实现方式欠妥**：把整句级谓词**复制给每个目标列** + **不隔离"值血缘/谓词血缘"子图**，副作用就是污染了值血缘，让影响分析把"行过滤"误判为"值影响"。

---

## 五、改进方向

1. **隔离两套血缘**：建"值血缘"和"谓词血缘"两个子图/关系类型。影响分析默认只走值血缘；想看行级依赖时再切谓词视图。
2. **影响分析默认排除条件 role**：图遍历时跳过 `role ∈ {join_condition, where_condition}`，除非用户显式勾选"含条件"。
3. **不要复制给每列**：条件字段挂到代表整句的 `RowFilter`/`JoinPredicate` 节点（或只保留在表级 `READS` 边的 JSON 属性里，那里本来就有）。
4. **把条件表达式本体也建模进去**（不只是字段），才能支持"改了 JOIN 条件逻辑会怎样"这类分析。

> 其中第 2 点（排除 condition role 开关）是改动量最小的修复，可立刻消除假阳性；第 4 点改动最大但价值最高。

---

## 六、一句话总结

字段级血缘图里**搜不到**独立的"ON 条件/WHERE 条件"节点：表级时它们藏在 `READS` 边的 JSON 属性里，字段级时它们"借壳"成 `Column` 节点、自身退化为 `INPUT_TO` 的 `role` 属性。问题在于字段级实现把整句级谓词复制进每个目标列的值来源，导致影响分析假阳性——根因是**谓词血缘与值血缘未隔离**。
