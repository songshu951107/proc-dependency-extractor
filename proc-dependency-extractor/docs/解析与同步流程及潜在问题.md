# 存储过程解析与 Neo4j 同步：完整流程梳理与潜在问题清单

## 1. 完整流程

```
脚本(.py)
   |  parser.parse()  [JsqlParser 4.9 语法树]
   v
ProcMetadata
   |  saveMetadata()  <- 逐 proc 先删后建
   v
MySQL(血缘真相源):
  proc_info / proc_table_dependency
  table_lineage / table_lineage_filter
  table_field_mapping / table_transform_input
  table_block_condition / sql_block_info
   |  syncProc()  <- 逐 proc 先删后建(deleteProcData)
   v
Neo4j(图加速层): Table/Column/Transform/关系
   +--> /api/impact/analyze  影响分析
```

两个环节都遵循 "逐 proc 先删后建"，无整库清空（除显式 clear-neo4j / deleteProc 外）。

### 1.1 解析（MySQL）
入口：extractAndSave / extractAndSaveBatch / reExtractAll / extractAndSaveUploaded
- parser.parse() 成功之后才进入 saveMetadata（解析失败则事务回滚，旧数据保留）。
- saveMetadata 按 proc_name 对 6 张血缘表先 DELETE 再 INSERT，并重建 proc_info（id 会变化）。
- 血缘写入顺序：edges -> block_condition(行血缘) -> filters -> field_mapping(+transform_input) -> sql_block_info。

### 1.2 同步（Neo4j）
入口：syncProc / resync / resync/all
- 第一步 deleteProcData(procName)：删除该 proc 的 READS/MAPS_TO/FILTERS 关系、Transform 节点(DETACH)、临时表 Column、Script 节点，并全局清扫孤立 Table/Column/Transform。
- 随后从 MySQL 重建 Table/Column/Transform 及 INPUT_TO/OUTPUT_TO/BELONGS_TO 等关系。

## 2. 潜在问题清单

### A. 一致性 / 漂移（最需关注）
1. 两端漂移无联动：MySQL 与 Neo4j 是两条独立操作链，系统无"reparse 后强制 resync"联动。只 reparse 不 resync -> Neo4j 仍旧图；只 resync 不 reparse -> Neo4j 反映旧血缘。任何错配都产出误导结果。
2. resync/all 同步长任务易超时中断：中断后 Neo4j 处于"部分 proc 新、部分旧"的混合态，直到本轮全量跑完。后续必须整段后台跑完，不能当快速请求。

### B. 事务 / 原子性
3. extractAndSaveBatch/reExtractAll 外层 @Transactional 包住整批循环，内部逐文件 try/catch——单文件失败只丢自己、不回滚他人（合理）；但一批在一个事务内对 299 个 proc 持续持锁，走 batch 接口时很长。（reparse_all.ps1 逐文件调 HTTP，规避了长事务。）
4. 解析失败被吞掉不抛，只进 failures 列表——无"失败即中止"的强制机制，调用方只能事后核对成功/失败计数。

### C. 数据残留 / 孤儿
5. 改名不留痕：saveMetadata 按 procName 删旧。若存储过程改名或文件改名，旧 procName 的 MySQL 血缘与 Neo4j 节点永不清除，形成孤儿数据，污染统计与影响分析（deleteProc 也只能按显式 procName 删）。
6. 同步只清理"该 proc 的 Transform/临时表列"+ 全局孤立节点，物理表共享节点不动（合理）。但 DWA 自产表没进 columns0818.xlsx 时无 DDL 元数据，裸列归属仍是盲区，需人工补表。

### D. 全局孤立清扫（重点风险）
7. deleteProcData 第 5 步孤立清扫是全局命令、无 proc 过滤：
   MATCH (n) WHERE (n:Table OR n:Column OR n:Transform) AND NOT (n)--() DELETE n
   - 它随任意一次 proc 同步执行，删除整个图中"零关系"的 Table/Column/Transform，范围超出"删当前 proc"。
   - 一般不会误删合法血缘：合法节点几乎都被 BELONGS_TO/INPUT_TO/OUTPUT_TO/READS 锚住；解析失败/同步失败的 proc 不是孤儿，不会被删。
   - 真正值得注意：局部清理带全局副作用；且 Neo4j 删除不随 MySQL 事务回滚（neo4jClient 操作不受 @Transactional(REQUIRES_NEW) 约束），重建中途异常会留下某 proc 在图中暂时缺省、两端短暂不一致。

### E. 图模型 / 多块写入
8. 同一物理列（如 int_income）现拆成多个独立 Transform（多个 DIRECT + LITERAL + SUM）。正确反映多 UNION 分支，但上游会显示多个并列父节点；logicType 推断一变，剪枝逻辑可能再断链，需回归测试守护。
9. transformId 依赖 MySQL 自增 fieldMappingId，reparse 会重生成 id。只要"先 reparse 后 resync"顺序对，旧 Transform 已删、按新 id 重建则安全；但若老 jar 与新 jar 实例并存，id 策略不一致会造成节点 key 冲突/残留（部署一致性）。

### F. 性能
10. 同步逐 proc DETACH DELETE + 重建，单线程串行、无批量 Cypher，299 个 proc 耗时较长，与问题 2 叠加加剧超时风险。

## 3. 建议（按性价比排序）
- 把"reparse 后须 resync + 重启新 jar"固化成校验/提示，或提供"reparse->resync 联动"一键入口。
- 将 resync/all 改为后台任务 + 进度查询，替代长 HTTP。
- 增加孤儿清扫任务（按 procName 差集清理 MySQL，并同步清理 Neo4j 孤立 Transform/Column）。
- 保留 130 个单测，把"多块写入列"场景纳入回归，防范问题 8。
